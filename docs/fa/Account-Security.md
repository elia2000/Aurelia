# امنیت حساب

دو چیز علاوه بر رمز عبور از حساب Aurelle شما محافظت می‌کند: می‌توانید **همه‌ی ورودها را ببینید و پایان دهید** (نشست‌های فعال)، و می‌توانید با یک برنامه‌ی احراز هویت **مرحله‌ی دوم** اضافه کنید (احراز هویت دو مرحله‌ای، 2FA). هر دو در **Settings → Security** هستند، هم در پنجره‌ی دسکتاپ و هم در پنل موبایل.

:::tip

احراز هویت دو مرحله‌ای **اختیاری** و برای هر فرد جداگانه است. جز اینکه سرور کلید مخفی معمول خود (`STORAGE_ENCRYPTION_KEY`، که در اولین اجرا ساخته می‌شود) را داشته باشد، چیزی از مدیر نمی‌خواهد. در Aurelle **بازیابی با ایمیل وجود ندارد**: پیش از روشن کردن آن بخش [اگر برنامه‌ی احراز هویت را از دست بدهید](#اگر-برنامه-ی-احراز-هویت-را-از-دست-بدهید) را بخوانید.

:::

## نشست‌های فعال

**Settings → Security → Active sessions** هر مرورگر یا برنامه‌ای را که به حساب شما وارد شده فهرست می‌کند:

- **این دستگاه** همیشه اول است و برچسب **This device** دارد. دکمه‌ی *Sign out* ندارد (از **Log out** در منو استفاده کنید).
- هر ردیف **مرورگر و سیستم‌عامل** («Firefox on Linux»)، **آخرین فعالیت** («5 minutes ago»، «yesterday»)، **زمان ورود** و روش ورود (رمز عبور، رمز عبور و کد، کد بازیابی، یا هنگام ساخت حساب) را نشان می‌دهد.
- **Sign out** کنار یک ردیف همان نشست را پایان می‌دهد. **Sign out all other devices** (ابتدا تأیید می‌گیرد) همه‌ی نشست‌ها جز این یکی را پایان می‌دهد.

### با دستگاهی که خارج می‌کنید چه می‌شود

خارج کردن یک نشست **فوراً** اثر می‌کند، نه در بازآوری بعدی صفحه:

| چه چیز | نتیجه |
|---|---|
| نشست | حذف می‌شود. هر درخواستی که آن مرورگر از این پس بفرستد با **401 Not authenticated** پاسخ داده می‌شود. |
| اتصال زنده | اتصال بلادرنگ باز آن مرورگر (SSE یا WebSocket) خبردار می‌شود که خارج شده و سپس **بسته می‌شود**، پس بلافاصله دیگر پیامی دریافت نمی‌کند. |
| مرورگر | اگر باز باشد به **صفحه‌ی ورود** می‌رسد با یادداشتی: *You were signed out from another device.* |
| اعلان‌های Push | اشتراک‌های اعلانی که آن مرورگر ثبت کرده **حذف می‌شود** و دیگر اعلان نمی‌گیرد. |
| کلید رمزنگاری | **کلید دستگاه** رمزنگاری سرتاسری که آن مرورگر ثبت کرده **باطل می‌شود** (به [پروتکل رمزنگاری](./E2EE-Protocol.md) نگاه کنید). دیگران دیگر پیام‌های ویدیویی جدید را برای آن رمز نمی‌کنند. اگر آن مرورگر دوباره وارد شود کلید دستگاه تازه‌ای ثبت می‌کند. |

**Log out** معمولی در یک دستگاه فقط همان نشست را پایان می‌دهد و اشتراک‌های Push آن را حذف می‌کند؛ کلید دستگاه را نگه می‌دارد، چون همان مرورگر به‌طور عادی دوباره وارد می‌شود.

چیزهای دیگری که نشست‌ها را به همین شکل پایان می‌دهند:

- **تغییر رمز عبور**، **همه‌ی دستگاه‌های دیگر** شما را خارج می‌کند (این یکی می‌ماند). دستگاه‌های دیگر به صفحه‌ی ورود می‌روند.
- **مسدود کردن شما توسط مدیر**، **بازنشانی رمز عبور** یا **بازنشانی احراز هویت دو مرحله‌ای** همه‌ی نشست‌های شما را پایان می‌دهد. حذف حساب هم همین‌طور.
- هر نشست از زمان ورود **۱۴ روز** اعتبار دارد (عمر کوکی). پس از آن سرور آن را رد و حذف می‌کند، حتی اگر کسی نسخه‌ای از کوکی را نگه داشته باشد.

### حریم خصوصی: یک نشست چه چیزی را به خاطر می‌سپارد

یک نشست **فقط خانواده‌ی مرورگر و سیستم‌عامل** («Chrome on Android») را ذخیره می‌کند که هنگام ورود از هدر `User-Agent` مرورگر گرفته می‌شود. **هیچ آدرس IP**، شماره‌ی نسخه یا هدر خام ذخیره نمی‌شود. Aurelle موقعیت مکانی نشان نمی‌دهد: IP کوتاه‌شده هم داده‌ی شخصی است، در نصب خودمیزبان پایگاه GeoIP وجود ندارد و حدس مبهم سود چندانی ندارد. محدودسازی نرخ IP را فقط در حافظه نگه می‌دارد و هرگز در پایگاه داده نمی‌نویسد. (گزارش اختیاری fail2ban قابلیتی جدا و انتخابی است؛ به یادداشت‌های مدیر نگاه کنید.)

فهرست همیشه فقط نشست‌های **خود شما** است. درخواست خروج نشست فرد دیگر یا نشستی که وجود ندارد همان پاسخ «Session not found» را می‌گیرد.

## احراز هویت دو مرحله‌ای (TOTP)

Aurelle از **رمز یک‌بارمصرف مبتنی بر زمان** استاندارد (RFC 6238، مثل Google Authenticator، Aegis، 1Password، Bitwarden، Authy ...) استفاده می‌کند: ۶ رقم، هر ۳۰ ثانیه، با تحمل یک گام به هر طرف برای ساعت کمی نادرست.

### روشن کردن

1. **Settings → Security → Two-factor authentication → Turn on.**
2. **رمز عبور فعلی** را وارد کنید (دوباره پرسیده می‌شود تا کسی با یک دستگاه بازِ بدون قفل نتواند آن را روشن کند).
3. **کد QR** را با برنامه‌ی احراز هویت اسکن کنید، یا **Open in authenticator app** را بزنید، یا **کلید راه‌اندازی** را دستی وارد کنید.
4. **کد ۶ رقمی** را که برنامه اکنون نشان می‌دهد وارد کنید و **Turn on** را بزنید. تا این یک کد درست نباشد هیچ چیز فعال نمی‌شود.
5. Aurelle **۱۰ کد بازیابی** نشان می‌دهد. **همین حالا کپی یا دانلودشان کنید: فقط یک بار نمایش داده می‌شوند.** *I saved my recovery codes* را تیک بزنید و **Done** را بزنید.

### ورود با 2FA

1. مثل همیشه نام کاربری و رمز عبور را وارد کنید.
2. اگر رمز درست باشد، Aurelle هنوز شما را وارد **نمی‌کند**. **Two-step verification** را نشان می‌دهد: کد فعلی برنامه را وارد کنید.
3. وارد می‌شوید. کد **یک بار** کار می‌کند: کدی (یا کد قدیمی‌تری داخل بازه‌ی تحمل) که قبلاً استفاده شده رد می‌شود.

محدودیت‌ها: برای هر تلاش ورود **۵ کد اشتباه** مجاز است؛ بعد از آن باید دوباره رمز عبور را وارد کنید. کدهای اشتباه یک حساب بین تلاش‌ها هم جمع می‌شوند (حسابی که زیاد جمع کند حدود ۱۵ دقیقه متوقف می‌شود). خود مرحله‌ی رمز عبور هم محدودیت نرخ دارد (پایین‌تر). فاصله‌ی بین رمز عبور و کد **۵ دقیقه** است.

### کدهای بازیابی

- **۱۰** کد با قالب `XXXXX-XXXXX` می‌گیرید. هر کدام **دقیقاً یک بار** کار می‌کند، به‌جای کد برنامه هنگام ورود، برای خاموش کردن 2FA یا برای گرفتن کدهای بازیابی جدید. حروف بزرگ/کوچک، خط تیره و فاصله اهمیتی ندارند.
- Aurelle فقط یک **هش کلیددار** از هر کد نگه می‌دارد. نمی‌تواند دوباره نشانتان دهد؛ **Get new recovery codes** (رمز عبور و یک کد) کل مجموعه را عوض می‌کند و کدهای قدیمی از کار می‌افتند.
- پنل Security تعداد باقی‌مانده را نشان می‌دهد و وقتی دو کد یا کمتر مانده هشدار می‌دهد.

### خاموش کردن

**Settings → Security → Two-factor authentication → Turn off** **رمز عبور و یک کد** (کد برنامه یا کد بازیابی) می‌خواهد. راز و همه‌ی کدهای بازیابی حذف می‌شوند.

### کارهای دیگری که کد شما را می‌خواهند

وقتی 2FA روشن است، **تغییر رمز عبور** و **حذف حساب** هم رمز عبور **و یک کد** می‌خواهند. فیلد *Authentication code* بار اول که سرور درخواست کند نمایش داده می‌شود.

### اگر برنامه‌ی احراز هویت را از دست بدهید

1. **هنوز یک کد بازیابی دارید:** با رمز عبور وارد شوید، **Use a recovery code instead** را بزنید و آن را وارد کنید. سپس 2FA را خاموش و دوباره روشن کنید تا راز جدید بگیرید (یا فقط کدهای بازیابی جدید بگیرید).
2. **نه برنامه را دارید و نه کد بازیابی:** بازنشانی با ایمیل وجود ندارد. از یک **مدیر** بخواهید احراز هویت دو مرحله‌ای شما را بازنشانی کند (**Admin panel → Users → Edit user → Two-factor authentication → Reset two-factor**). این کار راز و کدهای بازیابی را حذف می‌کند و شما را **از همه‌جا خارج می‌کند**. بعد فقط با رمز عبور وارد می‌شوید و می‌توانید دوباره 2FA را راه بیندازید. مدیر رمز عبور شما را نمی‌بیند و نمی‌تواند به‌جای شما وارد شود؛ بازنشانی فقط مرحله‌ی دوم را برمی‌دارد و در گزارش ممیزی با نام `user.reset_2fa` ثبت می‌شود.
3. **شما مالک و تنها مدیر هستید:** مدیر نمی‌تواند 2FA مالک را بازنشانی کند، پس کدهای بازیابی را نگه دارید. به‌عنوان آخرین راه، حساب مالک را می‌توان از روی سرور با [دستورات دیتابیس](./Database-Commands.md) بازیابی کرد.

## چگونه محافظت می‌شود (برای مدیران)

- **راز در حالت ذخیره.** راز TOTP (۱۶۰ بیت تصادفی) با AES-256-GCM **رمز شده** ذخیره می‌شود. کلید با HKDF-SHA-256 از `STORAGE_ENCRYPTION_KEY` ساخته می‌شود، رازی که Aurelle خودش در اولین اجرا می‌سازد و برای ذخیره‌ی پیام‌ها استفاده می‌کند، با برچسب هدف مخصوص خودش، پس همان کلیدی نیست که از پیام‌ها محافظت می‌کند. شناسه‌ی کاربر مالک جزو داده‌ی احرازشده است، پس ردیفی که به کاربر دیگر کپی شود رمزگشایی نمی‌شود. اگر `STORAGE_ENCRYPTION_KEY` نباشد، 2FA روشن نمی‌شود (هرگز رازی را به‌صورت متن ساده ذخیره نمی‌کند). **آن کلید را نگه دارید:** اگر گم شود رازهای ذخیره‌شده خوانده نمی‌شوند و کاربران 2FA به بازنشانی مدیر نیاز دارند (کدهای بازیابی‌شان هم کار نمی‌کند).
- **کدهای بازیابی** با HMAC-SHA-256 زیر کلیدی مشتق از همان راز ذخیره می‌شوند، پس نسخه‌ی دزدیده‌شده‌ی پایگاه داده برای حدس زدن آفلاین آن‌ها کافی نیست. یک‌بارمصرف‌اند و به‌صورت اتمی مصرف می‌شوند.
- **محافظت در برابر بازپخش.** گام زمانی آخرین کد پذیرفته‌شده ذخیره می‌شود؛ کد فقط برای گام **بعدی** پذیرفته می‌شود.
- **چالش (challenge).** بعد از رمز درست، سرور به‌جای نشست یک توکن امضاشده‌ی **۵ دقیقه‌ای** با یک هدف (HMAC) برمی‌گرداند. کوکی نیست و هیچ مسیر دیگری آن را نمی‌پذیرد. بعد از یک استفاده‌ی موفق سوخته می‌شود و بعد از ۵ کد اشتباه قفل می‌شود.
- **زمان ثابت.** کدها و توکن‌ها در زمان ثابت مقایسه می‌شوند. نام کاربری ناشناخته هم یک مقایسه‌ی هش رمز هزینه دارد، پس زمان پاسخ نشان نمی‌دهد کدام حساب‌ها وجود دارند؛ خطا همان `Invalid credentials.` است.
- **محدودسازی نرخ.** بررسی‌های ناموفق رمز و کد به‌ازای IP و حساب، به‌ازای حساب و به‌ازای IP محدود می‌شوند (حدود ۸، ۳۰ و ۶۰ خطا در ۱۵ دقیقه) و با `429 Too many attempts` و `Retry-After` پاسخ می‌دهند. همان محدودیت از تغییر رمز، حذف حساب و مسیرهای 2FA هم محافظت می‌کند، پس کوکی دزدیده‌شده برای حدس زدن رمز قابل استفاده نیست. وضعیت در حافظه و برای هر پردازش است.
- **وضعیت مسدودی.** حساب مسدود فقط بعد از رمز درست به‌عنوان مسدود گزارش می‌شود؛ رمز اشتباه همان `Invalid credentials.` معمولی را می‌گیرد.
- **شناسه‌ی نشست تازه.** هر ورود یک توکن تصادفی جدید (۱۹۲ بیت) می‌سازد. توکنی که مرورگر بفرستد هرگز پذیرفته نمی‌شود و نشستی که مرورگر پیش‌تر داشت حذف می‌شود.
- **کوکی.** `sid` با `HttpOnly`، `SameSite=Lax`، `Path=/`، `Max-Age` برابر ۱۴ روز، و روی HTTPS با `Secure` است (وقتی `APP_ENV` برابر production باشد، که پیش‌فرض است).
- **لاگ‌ها.** وقتی `APP_DEBUG` روشن باشد، بدنه‌ی درخواست و پاسخ لاگ می‌شود، **با پوشاندن رمز عبور، کدها، کدهای بازیابی، چالش‌ها و رازها**.

### پایگاه داده

مهاجرت **050** ستون‌های `sessions.public_id` (شناسه‌ی تصادفی که API به‌جای توکن نشان می‌دهد)، `user_agent` و `auth_method` را اضافه می‌کند و اشتراک‌های Push و دستگاه‌های E2EE را به نشستی که ثبتشان کرده پیوند می‌دهد. مهاجرت **051** جدول‌های `user_two_factor` و `user_recovery_codes` را اضافه می‌کند. هر دو را می‌شود بارها اجرا کرد و روی SQLite و PostgreSQL کار می‌کنند.

## خلاصه‌ی API

همه‌ی مسیرها نشست واردشده می‌خواهند مگر ذکر شده؛ بدنه‌ها JSON هستند.

| مسیر | هدف |
|---|---|
| `GET /api/sessions` | نشست‌های شما: `id`، `current`، `device`، `browser`، `os`، `method`، `viaPassword`، `createdAt`، `lastSeenAt`. هرگز توکن نیست. |
| `DELETE /api/sessions/:id` | یکی را خارج می‌کند. اگر مال شما نباشد `404`. نشست فعلی یک Log out معمولی است. |
| `POST /api/sessions/revoke-others` | همه‌ی نشست‌ها جز این یکی را خارج می‌کند. |
| `GET /api/2fa` | `{ available, enabled, enabledAt, recoveryCodesRemaining }` |
| `POST /api/2fa/setup` | `{ password }` ← `{ secret, otpauthUri, ... }` (هنوز فعال نیست) |
| `POST /api/2fa/enable` | `{ code }` ← `{ recoveryCodes }` (یک بار نمایش) |
| `POST /api/2fa/recovery-codes` | `{ password, code یا recoveryCode }` ← کدهای جدید |
| `POST /api/2fa/disable` | `{ password, code یا recoveryCode }` |
| `POST /api/login` | برای حساب 2FA کوکی نشست نمی‌دهد: `{ twoFactorRequired: true, challenge }` |
| `POST /api/login/2fa` | `{ challenge, code یا recoveryCode }` ← وارد می‌کند (بدون نیاز به احراز هویت) |
| `PUT /api/password`، `POST /api/profile/delete` | با 2FA روشن تا وقتی `code` یا `recoveryCode` فرستاده نشود `401 { twoFactorRequired: true }` می‌دهند. |
| `POST /api/admin/users/:id/reset-2fa` | مدیر: 2FA یک کاربر را برمی‌دارد و نشست‌هایش را پایان می‌دهد. |

فهرست کاربران مدیر هم کنار کسانی که 2FA دارند یک آیکون کلید نشان می‌دهد. به [پنل مدیریت](./Admin-Panel.md) نگاه کنید.
