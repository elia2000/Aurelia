# نگهداری امنیتی

امن نگه داشتن سرور Aurelle بیشتر یک روال تکراری است: برنامه را به‌روز کنید، Node.js را جدید نگه دارید و گاهی گزارش امنیتی وابستگی ها را ببینید. این صفحه همین روال را توضیح میدهد. برای گزارش یک آسیب‌پذیری [سیاست امنیتی](https://github.com/elia2000/Aurelia/security/policy) را ببینید.

| هر چند وقت | چه کاری |
|---|---|
| وقتی نسخه جدید اعلام شد | به‌روزرسانی Aurelle |
| تقریبا ماهی یک بار | بررسی وابستگی ها و نسخه Node.js |
| یک بار، روی سرور عمومی | راه اندازی [Fail2ban](./Fail2ban.md) تا اسکریپتی که رمز حدس میزند مسدود شود |

## به‌روزرسانی Aurelle

نسخه های جدید شامل اصلاحات امنیتی و وابستگی های به‌روز هستند، پس این مفیدترین کاری است که میتوانید انجام دهید. روش کامل، همراه با دانگرید و پشتیبان گیری از پایگاه داده، در صفحه [به‌روزرسانی](./Updating.md) آمده است. خلاصه:

### اسکریپت نصب

```bash
songbird-deploy
```

گزینه **Update Aurelle** را انتخاب کنید. اسکریپت پیشنهاد پشتیبان گیری از پایگاه داده میدهد، کد جدید را میگیرد، وابستگی ها را از روی فایل های lock نصب میکند (`npm ci`؛ فقط اگر فایل lock هماهنگ نباشد `npm install` به عنوان جایگزین)، کلاینت را دوباره میسازد، مهاجرت های پایگاه داده را اجرا میکند و سرویس ها را راه اندازی مجدد میکند.

### نصب دستی (systemd)

ابتدا از پایگاه داده پشتیبان بگیرید (`npm run db:backup` در پوشه `server/`)، سپس:

```bash
cd /opt/songbird
git pull --ff-only origin main

# Install exactly what the lock files say; `npm ci` never rewrites them.
npm --prefix server ci
npm --prefix worker ci
npm --prefix client ci

npm --prefix client run build
(cd server && npm run db:migrate)

sudo systemctl restart songbird songbird-worker
```

اگر در `/opt/songbird` نصب نکرده اید مسیر را عوض کنید. این دستورها را با کاربری اجرا کنید که مالک نصب است، مثل [نصب دستی](./Manual-Installation.md).

### Docker

```bash
cd /path/to/aurelle
git pull --ff-only origin main
docker compose up -d --build
```

ساخت ایمیج خودش `npm ci` را اجرا میکند. کانتینر `nginx` از فایل `nginx/nginx.conf` مخزن استفاده میکند، پس با pull آن هم به‌روز میشود؛ اگر این فایل تغییر کرده بود یک بار دیگر `docker compose up -d` بزنید.

:::tip

روی سرور از `npm ci` استفاده کنید نه `npm install`. `npm ci` دقیقا نسخه های `package-lock.json` را نصب میکند و اگر فایل lock با `package.json` هماهنگ نباشد با خطا متوقف میشود؛ یعنی چیزی که اجرا میشود همان چیزی است که آزمایش شده.

:::

## نسخه Node.js

Aurelle به **Node.js نسخه 24.18 یا جدیدتر** و **npm نسخه 11.18 یا جدیدتر** نیاز دارد (فیلد `engines` در `package.json`). ببینید سرویس از چه نسخه ای استفاده میکند:

```bash
node -v
npm -v
```

اگر قدیمی تر بود، Node.js 24 جدید را به همان روشی نصب کنید که بار اول نصب کردید (NodeSource، nvm یا Volta، در [نصب دستی](./Manual-Installation.md))، وابستگی ها را مثل بالا با `npm ci` دوباره نصب کنید و سرویس ها را راه اندازی مجدد کنید. ماژول های بومی مثل `better-sqlite3` برای یک نسخه مشخص از Node ساخته میشوند و بعد از ارتقای Node باید دوباره نصب شوند. گزینه **Update Aurelle** در اسکریپت نصب این کار را برای شما انجام میدهد.

از یک شاخه نسخه (LTS) استفاده کنید که هنوز اصلاحات امنیتی میگیرد؛ فهرست آن ها در [nodejs.org/en/about/previous-releases](https://nodejs.org/en/about/previous-releases) است.

## بررسی وابستگی ها

`npm audit` نسخه های موجود در فایل lock را با پایگاه داده عمومی آسیب‌پذیری ها مقایسه میکند. آن را در هر بخش پروژه اجرا کنید:

```bash
cd /opt/songbird
for dir in server worker client; do
  echo "== $dir"; (cd "$dir" && npm audit --omit=dev)
done
```

`--omit=dev` گزارش را به چیزهایی محدود میکند که واقعا روی سرور میروند. سهم هر بخش:

| بخش | در محیط واقعی اجرا میشود؟ | توضیح |
|---|---|---|
| `server/` | بله | سرور API. وابستگی های اجرایی آن (`express`، `compression`، `ws` و ...) همه درخواست ها را پردازش میکنند. |
| `worker/` | بله | ورکر مدیا. |
| `client/` | بله، ولی فقط به شکل فایل های ساخته شده | وابستگی های اجرایی آن (`react`، `dompurify`، `marked` و ...) داخل برنامه وب قرار میگیرند و مرورگر کاربران آن ها را اجرا میکند. اول به این ها برسید. |
| ریشه (`package.json`) | خیر | سایت مستندات و ابزار انتشار نسخه. هیچ وقت روی سرور نصب نمیشود. |

بقیه چیزهای فایل های lock (ابزار تست، ابزار ساخت، لینتر) فقط روی دستگاه توسعه دهنده یا در CI اجرا میشوند. `npm audit` بدون `--omit=dev` آن ها را هم فهرست میکند؛ اهمیتشان خیلی کمتر است ولی اگر رفع آن ها آسان بود بهتر است به‌روز شوند.

### رفع مواردی که گزارش پیدا میکند

```bash
cd server            # or worker, or client
npm audit fix        # patch and minor updates inside the ranges in package.json
npm test             # or the checks below
```

- از `npm audit fix --force` **استفاده نکنید**. این دستور نسخه اصلی (major) را تغییر میدهد، گاهی نسخه را پایین میبرد و ممکن است برنامه را خراب کند. اول توضیح آسیب‌پذیری را بخوانید و تصمیم بگیرید.
- `npm audit fix` فایل `package-lock.json` را تغییر میدهد. تفاوت را بررسی کنید: فقط بسته های نام برده شده در گزارش و وابستگی هایشان باید عوض شوند.
- اگر برای یک آسیب‌پذیری **هنوز نسخه اصلاح شده ای وجود ندارد** (`npm audit` مینویسد "No fix available")، چیزی برای نصب نیست. بررسی کنید آیا کد آسیب‌پذیر در Aurelle قابل دسترس است و منتظر انتشار اصلاح باشید.
- بسته هایی که فقط از طریق ابزاری گزارش میشوند که روی سرور اجرا نمیشود (مثلا ابزار انتشار نسخه در پروژه ریشه) میتوانند منتظر بمانند.
- بعد بررسی های مربوط به بخشی که تغییر داده اید را اجرا کنید: `npx vitest run` در `server/` و `worker/`؛ در `client/` دستورهای `npx vitest run --project unit` و `npx eslint src test` و `npm run build`؛ و `npm run docs:build` در ریشه.

:::info

بسته های `vitest` (یعنی `vitest`، `@vitest/browser`، `@vitest/browser-playwright`، `@vitest/coverage-v8` و `@vitest/ui`) دقیقا همان نسخه یکدیگر را میخواهند. اگر یکی را دستی به‌روز میکنید، همه را با هم در `package.json` بالا ببرید؛ وگرنه npm با خطای `ERESOLVE` متوقف میشود.

:::

### درخواست های به‌روزرسانی خودکار

مخزن از GitHub Dependabot استفاده میکند (`.github/dependabot.yml`): ماهی یک بار برای هر بخش یک pull request با به‌روزرسانی وابستگی ها باز میشود. بعد از موفق بودن تست ها آن ها را merge کنید. به‌روزرسانی های کوچک و پیوسته امن ترین راه جدید ماندن است.

### اگر `npm audit` اجرا نشد

`npm audit` باید به رجیستری npm دسترسی داشته باشد. پشت پراکسی یا بدون اینترنت با خطای شبکه متوقف میشود و خروجی مفیدی نمیدهد. آن را روی دستگاهی اجرا کنید که دسترسی دارد و نسخه ای یکسان را checkout کرده (چیزی که بررسی میشود فایل های lock است نه `node_modules` نصب شده). دستور `npm ls` نسخه های نصب شده را نشان میدهد.

## بعد از یک به‌روزرسانی امنیتی

1. بررسی کنید سایت باز میشود و میتوانید وارد شوید: `curl -s https://your-domain/api/health`.
2. لاگ سرویس را برای خطا ببینید: `sudo journalctl -u songbird -n 50`.
3. مرورگر را کامل تازه کنید (یا برنامه نصب شده را ببندید و دوباره باز کنید) تا فایل های جدید کلاینت بارگذاری شوند.
